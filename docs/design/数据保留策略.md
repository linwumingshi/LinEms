# 数据保留策略（D-02/D-04）

> 日期：2026-08-10 ｜ 目的：为增长数据定义保留期与滚动清理机制，防磁盘无限增长

## 1. 保留矩阵

### 1.1 Kafka topic（滚动清理 = 保留策略，KafkaRetentionInitializer 收敛）

| topic | 用途 | 保留期 | 说明 |
|---|---|---|---|
| `iot-raw` | 原始报文留痕（access 写，无消费方） | **24h** | 量大，仅近期追踪/补数 |
| `iot-thing-property` | 标准化属性上报 | 7 天 | 下游落库后仅作重放 |
| `iot-thing-event` | 标准化事件 | 7 天 | 同上 |
| `iot-device-lifecycle` | 上下线事件 | 7 天 | 同上 |
| `mqtt.uplink/down/broadcast` | 路由信封 | 7 天 | Kafka 默认，可调 |
| 其余业务 topic | — | Kafka 默认 7 天 | 按需收敛 |

### 1.2 MySQL 表（滚动清理 = 每日定时批删，各模块 RetentionCleaner）

| 表 | 模块 | 时间列 | 保留期 | 清理任务 |
|---|---|---|---|---|
| `iot_shadow_history` | energy-shadow | create_time | **7 天** | ShadowHistoryRetentionCleaner |
| `iot_device_online_record` | energy-device | create_time | **30 天** | OnlineRecordRetentionCleaner |
| `iot_command` | energy-command | create_time | **90 天** | CommandRetentionCleaner |
| `iot_alarm_record` | energy-alarm | triggered_time | **180 天** | AlarmRetentionCleaner |
| `sys_operator_log` | energy-system | create_time | **90 天** | OperatorLogRetentionCleaner |
| `ems_execution_record` | energy-ems | execute_time | **90 天** | ExecutionRecordRetentionCleaner |

## 2. 清理机制

- **触发**：每日 03:30（@Scheduled cron `0 30 3 * * *`），与业务高峰错峰。
- **互斥**：R-01 分布式锁（`lock:retention:{task}`），多实例仅一个执行清理。
- **批删**：`DELETE ... WHERE time_col < cutoff LIMIT 500` 循环至删不满一批，
  避免一次性大事务锁表/长事务；单批上限 500。
- **容错**：清理失败仅记日志，次日重试；删除阈值按保留矩阵配置（代码常量）。

## 3. 补充说明

- 权威数据在业务表（iot_command/iot_alarm_record 等）内保留期内可查；超期记录按合规/审计需求
  由归档任务（Phase 3 规划）先行搬运至归档库再删除。
- 时序数据（TDengine）按数据库自身保留策略（KEEP）管理，不在此矩阵。
- 删除是不可逆操作：上线前请按保留矩阵与业务/合规确认各保留期。
