# Phase：OTA 子集灰度（指定设备 + 灰度递进）

## 1. 背景与目标

当前 OTA 三种任务类型（`OtaTaskRow.taskType`）中，**「指定设备」(2)** 与 **「灰度」(3)** 互斥：

- `taskType=2 指定设备`：快照选中的设备子集，但 `grayBatchLimit` 在 `taskType != 3` 时直接返回 `-1`，选中设备**一次性全量**下发，无百分比截断。
- `taskType=3 灰度`：`parseTargetDevices` 快照**产品下全部设备**，`deviceCount` = 全量；灰度百分比相对"全产品"计算。

用户诉求：**能否"在选中的一部分设备内做灰度"**（指定子集 + 子集内按 1%→10%→50%→100% 递进）。

合理性：

- 多租户 / 多站点场景下，常只需对特定客户 / 站点的设备子集做灰度，无需波及全产品人群；全产品灰度对单站点问题无意义，反而扩大爆炸半径。
- 该需求是现有「指定设备」(子集·一次性) 与「灰度」(全量·分批) 的自然合取，为两者**严格超集**。

业界对照：

- **AWS IoT Jobs**：Job 直接 targeting 一个 Thing Group（子集）+ 配置 rollout rate（linear / exponential），原生支持"选设备组 + 限速分批"。✅
- **华为云 IoT**：升级任务「升级范围=指定设备」+「分批下发」（可配批次数 / 批间隔），指定子集内分批原生支持。✅
- **阿里云 IoT**：标准控制台「全部 / 定向 / 灰度」为互斥单选，灰度 % 对全产品人群计算，定向不按比例；标准模型无直接组合，需"定向 + 自拆多任务"近似。⚠️

## 2. 可行性（关键发现）

灰度引擎已是**子集感知**的，与"全产品 / 子集"无关：

- `dispatchPending`（OtaTaskService L243）遍历的是任务目标快照表 `OtaTaskDeviceRow`，而非产品全量。
- 批次上限 = `ceil(deviceCount × ratio / 100)`，而 `deviceCount` 是**快照时写入的总数**。

因此灰度的"百分比分母"完全由快照时的 `deviceCount` 决定。只要把 `deviceCount` 在快照时设为**选中子集数量**（而不是全产品），并放开灰度闸门（`grayBatchLimit` / `advanceGray` 的 `taskType==3` 判断），即可实现"在选中的 N 台里按比例递进"。改动面很小。

## 3. 方案（推荐：最小改动，新增 `taskType=4`）

保持 `taskType` 单枚举，新增一个值，避免引入新列与新维度带来的连锁重构：

| taskType | 目标范围 | 下发策略 | 说明 |
|---|---|---|---|
| 1 | 全部产品设备 | 立即全量 | 现状不变 |
| 2 | 指定设备子集 | 立即全量 | 现状不变 |
| 3 | 全部产品设备 | 灰度递进 | 现状不变 |
| **4** | **指定设备子集** | **灰度递进** | **新需求** |

### 3.1 后端改动（energy-ota）

1. `OtaTaskRow.taskType` 注释补充 `4 指定设备灰度`；`deviceCount` 语义不变（= 目标快照总数）。
2. `parseTargetDevices`（OtaTaskService L622）：`taskType ∈ {2, 4}` → 快照选中 `deviceIds` 子集，`deviceCount` = **子集大小**；`taskType ∈ {1, 3}` → 快照产品全部设备（保持现状）。
3. `grayBatchLimit`（L263）：放行条件由 `taskType == 3` 改为 `taskType == 3 || taskType == 4`。
4. `advanceGray`（L344）：放行条件同上（否则 `advanceGray` 会抛"非灰度任务"）。
5. 创建校验（`create`）：`taskType == 4` 必须带 `deviceIds` 且非空、`grayRatio` 合法（1–100）；响应式文案提示"将在选中的 N 台设备内按比例 1%→10%→50%→100% 递进"。
6. 列表 / 详情的 `taskType` 文本与徽标补充"指定设备灰度"。
7. **无需新增 DB 列**，复用现有 `taskType + deviceIds + grayRatio + deviceCount`。

### 3.2 前端改动（OtaTask.vue）

- 创建表单"指定设备"模式下，下发策略增加 **「灰度递进」** 选项（与"全部设备"下的灰度同理）；勾选后 `taskType=4`，并展示灰度比例输入与档位说明（1%→10%→50%→100%，成功率 <95% 自动暂停）。
- 设备多选弹窗复用现有 `listPickerDevices`（升级包驱动 + 关键字 / 状态筛选）。
- 任务列表 `TASK_STATUS` / 类型徽标补充 `4` 的展示。

### 3.3 兼容性

- 旧任务 `1 / 2 / 3` 行为完全不变；新 `taskType=4` 向后兼容（老前端版本不识别时显示为未知类型，不影响后端下发逻辑）。
- **可选增强（本期不推荐）**：将 `taskType` 拆为 `scope`(1全部/2指定) × `rolloutMode`(IMMEDIATE/GRAY) 两列，模型更干净、便于未来任意组合；但属更大重构，需同步改 DTO、校验、前端四态矩阵、历史数据迁移，投入明显高于收益。

## 4. 验证

- **单元 / 冒烟**：创建 `taskType=4` 任务，选 10 台设备，`grayRatio=1` → 首批 `ceil(10×1/100)=1` 台；成功率 ≥95% 推进 10%→1 台、50%→5 台、100%→10 台；验证批次上限随 `deviceCount`(=10) 变化，而非全产品数量。
- **回归**：历史 `taskType=3` 灰度行为不变；`taskType=2` 选中设备仍一次性全量。
- **边界**：小子集（如 3 台）首档 `ceil(3×1/100)=1` 台，合理；子集内设备离线保持 PENDING 等补推，不计入完结（现有逻辑已处理）。

## 5. 风险与待办

- 灰度档位 `GRAY_STEPS = {1, 10, 50, 100}` 为全局固定；子集极小时首档设备数可能为 1，属预期。
- 需在 `scanScheduledStart` / `advanceGrayScan` 调度中确认对 `taskType=4` 的 PENDING / RUNNING 状态处理与 `3` 一致（复用同一分支即可）。
- 前端"指定设备灰度"选项的可见性：仅在"指定设备"且用户切换为灰度策略时出现，避免与"全部设备灰度"混淆。
