# Phase10 户用储能模块设计审查（Design Review）

> 版本：v0.1 ｜ 日期：2026-08-13 ｜ 类型：设计草案审查
> 审查对象：`docs/design/Phase10-户用储能（Residential-Storage）模块设计.md`（v0.1 草案）
> 审查方式：**基于真实代码核对**（energy-* 模块源码 grep + 阅读），非文档自评。所有结论标注证据位置。

---

## 一、结论

草案的整体方向（**户用 = 资产子类 + 策略族，最大化复用现有平台**）成立。经代码核实，10 项"可复用"假设中 **8 项成立**：设备状态机、指令下行+ACK 闭环、设备影子(desired/reported)、独立网关、TDengine 超级表、MyBatis-Plus 行级租户、Kafka 消息总线、EMS 策略体系均可直接复用，且 `DR/SOC_CTRL 不产计划`的表述与代码一致（`StrategyType.java:58-60` 的 `isGeneratable()` 仅含 PEAK_VALLEY/DEMAND/TIME）。

但存在 **3 处与真实代码不符**（其中 1 处连简历表述都受影响）、**2 处文档内部矛盾**、**6 处设计缺口**，需在 v0.2 修订。详见下。

---

## 二、与真实代码不符（P0 必改）

### P0-1 `Station` 没有 station_type 字段
- 文档 §2.2 写"`Station.station_type` 新增枚举 HOME（默认 INDUSTRIAL）"。
- 事实：`energy-station/.../entity/Station.java:54` 只有 `gridType` 字段；枚举 `GridType.java:12` 为 `COMMERCIAL_INDUSTRIAL / PARK / GRID`，无 stationType/type。
- **改法**：扩展现有 `GridType` 枚举新增 `HOME`（优先，改动最小），或新增 `stationType` 字段并全链路透传。文档措辞需同步。

### P0-2 设备类型是固定枚举，加"户用一体机"需改代码
- 文档 §2.2/§3.2 假设新增 `device_type = RESIDENTIAL_AIO` 即可。
- 事实：`DeviceType.java:12-13` 是 7 种固定值枚举，`Device.java:50` 的 `deviceType` 字段为枚举类型——**新增需改枚举**；而 `Product.java:37` 的 `deviceType` 是 `String` 可容纳新值；物模型是"产品+版本+整份 JSON Schema"（`ThingModel.java:38` `schemaJson`），**非细粒度测点表**。
- **改法**：文档明确"DeviceType 枚举需新增 RESIDENTIAL_AIO + 字典"，物模型测点以 `schemaJson` 承载，勿暗示存在独立测点表。

### P0-3 TDengine 无连续查询/降采样（文档表述错误，且影响简历）
- 文档 §5 写"TDengine 超级表自动建表 + **连续查询降采样**"。
- 事实：`TdengineSqlBuilder.java:89` 超级表 `st_prop_{productKey}` 自动建表**属实**；但全仓搜索 `INTERVAL / CREATE CONTINUOUS / downsampl` **无结果**——**没有连续查询/降采样实现**。
- **影响**：① 文档 §5 需删改（改为"降采样需新增"，且户用 per-min 高频场景下是硬需求）；② 简历 `resume-linxx-ruiyi-backend.md` EnergyX 第 5 条写了"TDengine 超级表自动建表 + 连续查询降采样"——**"连续查询降采样"无代码支撑，建议一并删改**（上轮刚强调过简历诚实性）。

## 三、文档内部矛盾（P1）

### P1-1 "不新建独立服务"与"新增 energy-residential 模块"冲突
- §1 原则写"不新建独立服务"，§3.1/§4.1 却提"新增 `energy-residential` 模块"。
- **改法**：明确 `energy-residential` 是 **Maven 库模块挂载到现有服务**（建议挂 ems 做策略、挂 access 做 vendor adapter），而非新微服务；或删除"不新建独立服务"的绝对表述。二选一，不要两头都留。

### P1-2 竞品对照表未内嵌
- §9 引"对照表提炼"，但 5 家竞品对比表在对话里、不在文档内。
- **改法**：把对比表附入 §9 或附录，文档自洽。

## 四、设计缺口（P1/P2）

| # | 缺口 | 说明 | 建议 |
|---|---|---|---|
| G1 | **本地优先/断网兜底**（P1） | 户用设备在家庭 Wi-Fi，云端断连时谁调度？竞品都是本地 EMS（PowerMesh 本地执行层） | 双层设计：云端生成计划模板 → 设备端本地执行；离线按最近计划/本地策略兜底。文档只谈了云端下发 |
| G2 | **激活流程归属不清**（P1） | "免电工扫码激活"是谁操作？平台是 B 端 | 主路径=**运营商代激活/批量导入**，户主自助为辅；否则引入 C 端 App，范围爆炸 |
| G3 | **规模与容量假设缺失**（P1） | 户用 per-min 遥测×万家庭：1 万家庭×(一体机+电表)×60 点/min ≈ 2 万点/s，Kafka 分区/TDengine 写入/影子 Redis 热key 都会受压 | 文档补"量级假设 + 依赖阶段3 容量框架验证"章节 |
| G4 | **C 端设备安全与 OTA**（P1） | mTLS 证书每台签发、弱口令、固件 OTA 平台没有 | 明确：准入复用 HMAC+nonce；证书生命周期 + OTA 为新设计点（或对接厂商 OTA） |
| G5 | **法规限值配置化**（P2） | 德 800W/荷 P1 协议逐国不同 | 包络硬约束做成 `country_code + 限值配置表`，勿写死 |
| G6 | **租户语义与验收指标**（P2） | ① "租户=运营商，家庭是运营商下资产"，避免把家庭当租户；② 草案无验收 KPI | ① 文档明确租户层级；② 补验收指标（家庭接入耗时、策略命中率、节省测算误差） |
| G7 | **电价/天气源降级**（P2） | 动态电价 API 拉不到/超限时策略怎么办 | 补降级策略（用最近可用电价/TOU 模板兜底） |
| G8 | **VPP 措辞过强**（P2） | "具备 VPP 雏形"——平台无聚合调度/需求响应接口 | 弱化为"远期方向"，或补聚合 API 规划 |
