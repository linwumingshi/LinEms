## 0. 执行摘要

- **EMS 执行闭环已打通**（08-10 `040d852` + `3f4cde9`）：策略 → 计划生成 → 包络校验 → TDengine 落点 → 到点下发 → ACK 回写 → 状态机收敛（完成/失败/超时防悬挂），前端波形叠加实际功率曲线。**08-08 UX 评估的 P0/P1 项全部完成**，P2 执行追踪也已完成。
- **但"已有功能"存在 10 处假闭环**：最伤的三处——(1) **分时电价对计划生成零影响**（`PlanGenerator` 从不读电价，`ems_electricity_price` 是"死业务"）；(2) **5 种策略类型只有 PEAK_VALLEY 真实现**，其余 4 种可保存可启用但生成 0 点；(3) **PCS 下发设备单电站写死**（`device_id` 硬编码 0，默认空配置直接报错）。
- **行业标配缺位**：收益核算/经济评估、需量管理、电站级实时遥测监控、SOH/RUL、电芯级一致性、运行报表、损耗/效率分析——市面工商业 EMS 的"盈利中枢"功能在本项目前后端均不存在。
- **路线图建议**：先修 10 处假闭环（P0，让已有功能真正生效），再做行业标配 5 项（P1，收益核算/需量管理/监控驾驶舱/SOH/电芯一致性），报表与运维闭环进 P2，AI 预测/现货交易/VPP 等留架构接口进 P3（不本地实现）。

**数据模型**

| 实体 | 表 | 关键字段 |
|---|---|---|
| EmsStrategy | `ems_strategy` | strategy_type（PEAK_VALLEY/DEMAND/DR/SOC_CTRL/TIME）、config(JSON)、priority、status(0草稿1启用2停用)、version |
| EmsPlan | `ems_plan` | plan_date、plan_type(1充2放3混合)、total_energy、plan_param(JSON)、status(0待执行1执行中2完成3已取消 **4失败**)、uk(station,date) |
| EmsElectricityPrice | `ems_electricity_price` | price_type(DEEP/PEEK/PEAK/FLAT/VALLEY)、start/end_time、price、valid_from/to、status |

| EmsExecutionRecord | `ems_execution_record` | command_id、device_id、action(CHARGE/DISCHARGE/STANDBY)、state(0待下发1已下发2成功3失败4超时)、params/result(JSON)、uk(plan,plan_time) |
| TDengine STABLE | `ems_plan_point` | ts/action/power_kw/soc + TAG station_id，子表 `plan_{stationId}` |

**完整闭环（状态流转/持久化/校验齐备）**

- **EmsPlanService**（模块核心）：`generate()`（查策略→查电价→查约束→PlanGenerator→SafetyEnvelopeValidator→TDengine 写点→计划头落库，三重防重复）；`dispatch()`（受理制：status=0→重跑包络→执行中→立即下发到期点）；`dispatchDuePoints()`（按 `(plan_id,plan_time)` 幂等到点下发 + 10min 补发窗口）；`refreshPlanStatus()`（状态机收敛，错过窗口补记超时防悬挂）。
- **EmsAckConsumer**：消费 `iot-command-ack`，按 commandId 回写执行记录 state 并触发状态收敛，幂等覆盖。
- **PlanExecutionScheduler**（每分钟）：到点下发 + 状态推进 + 昨日遗留计划收尾。
- **ExecutionRecordRetentionCleaner**（`@XxlJob` 03:30，90 天清理）。
- **CommandClient**：HTTP 调 energy-command `POST /api/command`，复用指令链路。
- **TdenginePlanWriter**：原生 TAOS-RS JDBC，写前幂等（先 DELETE 当日点再 INSERT）。

**定时任务（3 个）**：`@XxlJob emsDailyPlanGenerate`（00:05，分布式锁）、`@XxlJob emsExecutionRetentionClean`（03:30）、`@Scheduled PlanExecutionScheduler`（每分钟，高频内部循环保留本地调度）。

**跨模块链路（完整）**

```
策略下发：EmsPlanService → CommandClient POST /api/command (commandType=2)
  → energy-command（deviceMapper 解析设备 → iot_command CREATED
      → 在线: Kafka iot-command-down → access → Broker QoS1 → PCS
      → 离线: Redis 离线队列 → 上线补发）
  → 设备 ACK → access → Kafka iot-command-ack
      → 双消费：energy-command（状态机）+ energy-ems EmsAckConsumer（回写执行记录）
```

## 4. 功能路线图（分四阶段）

优先级原则：**先修假闭环（已有功能真正生效）→ 再做行业标配业务功能 → 报表运维闭环 → 前沿留接口**。每项给依赖与验收口径。

### 阶段 P0 — 修复假闭环（8 项，让已有功能闭环）

| # | 任务 | 说明 | 依赖 | 验收 |
|---|---|---|---|---|
| P0-1 | **电价打通计划生成** | `PlanGenerator` 读 `in.prices()`：峰谷时段自动推导充/放窗口（或校验手工窗口与电价档一致），输出 `plan_param` 记录电价快照；生成期只取 status=1 且在有效期内档位 | 无 | 配置电价后生成计划窗口与峰谷档对齐；停用/过期电价不参与 |
| P0-2 | **PCS 按电站配置** | 下发设备从设备表解析（productKey+PCS 设备类型），支持一电站多 PCS；`device_id` 不再硬编码 0；消除"未配置下发设备"裸报错 | energy-device 查询或配置表 | 多电站各下各的 PCS；执行记录 device_id 真实 |
| P0-3 | **安全包络补全** | `temp_max` 生效；`voltage_max`/`current_max` 非空才校验；`safety_envelope` JSON 扩展纳入 | 无 | 超温/超压计划被拒绝或裁剪有原因 |
| P0-4 | **策略类型落地** | 至少 DEMAND（需量）、TIME（时间策略）补 `PlanGenerator`；DR/SOC_CTRL 明确语义或标注不可用；前端同步 `STRATEGY_GENERATABLE_TYPES` | P0-2（DEMAND 需设备） | 4 类型至少 2 个可生成非空计划 |
| P0-5 | **数据治理 + 电价管理** | 策略 config JSON schema 校验（保存即报，含窗口 start<end、功率≤包络）；电价 batchSave 改 upsert 幂等；**新增分时电价管理页面**（档位表 + 有效期增删改，承接 `priceApi`，当前 priceSave 无调用方）；`resolveStrategy` 校验 status=1 | P0-1 ✓ | 错误配置保存即提示；重复提交电价不叠行；页面可增删改电价并即时影响计划生成；草稿策略不能生成 |
| P0-6 | **计划质量字段** | 生成时计算 `total_energy`（Σ power×时长）、推导 `plan_type`（纯充/纯放/混合） | P0-1 | 前端表格显示真实总量与类型 |
| P0-7 | **影子 SOC 接线** | 初始 SOC 取 energy-shadow 影子实时值，无影子回退包络中点 | energy-shadow 查询 ✓ | 计划起点贴合真实 SOC |
| P0-8 | **ems-plan 事件产出** | `EMS_PLAN` topic 生产计划生成事件（`{stationId}` key），供 report/审计/未来 AI 消费 | 无 | Kafka 可看到 ems-plan 消息 |

### 阶段 P1 — 行业标配业务功能（5 项）

| # | 任务 | 说明 | 依赖 | 验收 |
|---|---|---|---|---|
| P1-1 | **收益核算/经济评估**（后端接口+前端页） | 日/月/年充放电量、峰谷套利收益、需量电费节省、ROI/回本周期；用执行记录 + 电价 + 功率曲线聚合 | P0-1/P0-6 | 电站收益页展示收益卡片与曲线，数据与执行记录一致 |

## 5. 建议实施顺序与工作量

**建议先做 P0-1 + P0-2**：它们分别解决"电价死业务"和"单设备写死"两个最伤的核心问题，且互不依赖，可并行。P0-3~P0-8 多为小改动，可在同一迭代内分批合入。**P0 完成后 EMS 才算真正闭环**：电价驱动计划、设备按站下发、包络完整、字段真实、事件可消费。

**P1 的 P1-1（收益核算）投入产出比最高**：数据（执行记录/电价/功率曲线）全在，是市面 EMS 差异化的直接体现，建议作为 P0 后的第一个独立迭代。

> 实施均按本仓库既有迭代流推进（brainstorming → spec → plan → subagent 执行 → 冒烟），勿并入其他迭代。
