## A. 项目总览与架构（5 题）

### A1. 一句话介绍 EnergyX 平台？
**考察点**：表达逻辑、抓重点能力。
**参考**：面向工商业储能的 IoT + EMS SaaS 平台，核心是「设备接入 → 实时遥测 → 能量调度 → 收益核算」完整闭环。资产链路覆盖集团→企业→电站→储能柜→电池簇→PCS→BMS→电芯，14 个微服务 + 自研高可用 MQTT Broker + Kafka 消息总线 + TDengine 时序存储，多租户运营。

### A2. 整体架构数据流怎么走？
**考察点**：是否真正掌握架构，而非背项目名。
**参考**：
```
设备(SDK/MQTT) → Broker(认证/限流/QoS) → Kafka[mqtt.uplink] → access 消费标准化
→ 业务模块(device/ems/alarm/tsdb/shadow) → 指令经 mqtt.down.{nodeId} 定向下发
→ 设备 ACK 反向上行 → 闭环驱动状态机
```
补充：下行还有 `mqtt.broadcast` 通道（KICK 踢线 / 死节点回落）；分层逻辑是「接入层 → 消息总线 → 消费处理 → 业务应用 → 存储」，各层横向可扩展。

### A3. 为什么自研 MQTT Broker，不用 EMQX / HiveMQ？⚠️（高频必问）
**考察点**：选型判断力、不迷信开源、有取舍。
**参考**：三个原因——
1. **深度定制**：设备凭据要对接自有鉴权体系（凭据失效秒级踢线），EMQX 走 webhook 有额外链路和延迟；我们下行按 `mqtt.down.{nodeId}` 业务定向路由，和指令 ACK 闭环强耦合，自研可控。
2. **能力沉淀**：连接锁租约、节点心跳 HA、共享订阅、发布限流这些核心机制沉淀为自己的资产。
3. **成本与演进**：商用授权成本 + 未来替换成本。
**补一刀（加分）**：我们阶段 3 正在评估 EMQX 做百万级集群替代对比——结论是 EMQX 千万连接成熟度确实高，自研优势在深度定制，若规模爆发、运维成本上升可平滑迁移，选型不是非此即彼。

### A4. 微服务怎么划分？服务间通信？
**参考**：按业务域划分：system/product/device/station/ems/access/tsdb/shadow/command/alarm/rule/notify/ota + mqtt-broker + gateway，共 14 个。同步调用走 OpenFeign（Nacos 注册发现），异步走 Kafka（遥测/告警/指令），跨模块状态用 Redis。拆分原则：领域聚合根 + 消息驱动解耦，避免跨库事务（用最终一致性）。

### A5. 「百万级设备接入」实际接入了多少？⚠️（口径必问）
**参考**：诚实拆分——
- **设计容量**：消息管线、Broker 集群、Kafka 分区、TDengine 分库全部按百万级规划；
- **实际规模**：当前十万级以内（工商业储能单体数量本身有限）；
- **容量经验来源**：物联网中台（百万级规模、单机 10w+ 长连接、5w+ 集中重连零故障），储能平台按同一方法论演进。
**补充 QPS 估算（主动讲，展示架构感）**：百万设备 × 10s 上报周期 ≈ 10 万 QPS 峰值，这是 Kafka 分区数、限流阈值、消费组设计的容量依据。

## B. MQTT Broker 核心深挖（12 题）⚠️ 全组高风险

### B1. QoS1 上行 PUBACK 49ms 怎么测的？什么环境？⚠️
**参考**：阶段 2 联调/压测环境实测基准值（内网、单 Broker 节点、设备模拟器批量上行），不是生产大数据量下的统计值。主动说明边界：**49ms 是基准值，生产上真正关注的是 P99、连接数增长下的退化曲线、GC 停顿与队列积压**。这么答既诚实又显专业。

### B2. QoS2「恰好一次」怎么实现？
**参考**（讲机制，这是硬核亮点）：
- **入站**：收到 PUBLISH(qos2) 先按 `deviceKey+packetId` 写入 Redis 缓存 → 回 PUBREC；**收到 PUBREL 才从缓存取出正式路由**（写 Kafka），Kafka 持久化确认后再回 PUBCOMP；重复 PUBREL 幂等直接确认（缓存缺失视为已完成）。
- **出站**：inflight 表状态机 `AWAITING_PUBREC → AWAITING_PUBCOMP`；PUBREC 丢失时收到重复 PUBREC 触发重发 PUBREL 防御。
- **核心一句话**：路由动作只发生一次，且与持久化确认绑定——「恰好一次」不是靠消息不重复，而是靠**幂等确认 + 状态机推进**。

### B3. 连接锁租约（Connection Lease）怎么设计？⚠️（追问最狠的点）
**参考**：
- Key：`mqtt:conn:{deviceKey} = nodeId`；SETNX 抢占 + **TTL 租约续期**（防节点挂掉锁永久占用）+ **Lua 脚本比较 owner 后释放**（防误删他人锁）。
- 同 deviceKey 新连接到达：owner 心跳存活 → 发 KICK 踢线再接管；owner 心跳消失 → 判定宕机，直接接管跳过踢线。
- 主动承认缺口：锁在 Redis 单点，脑裂可能双主；演进方向 etcd lease（强一致 + 会话自动过期）。

### B4. 节点宕机后会话/订阅/离线消息怎么恢复？多久？⚠️（诚实答法，别吹"秒级自动接管"）
**参考**：
- 会话/订阅/离线消息**全量外置 Redis（按 deviceKey）**，不依赖节点本地状态；
- 宕机后：设备 TCP 断开 → 重连到任意存活节点 → 查连接锁发现 owner 心跳 key 消失（最坏 30s TTL）→ **直接接管** → 从 Redis 恢复会话订阅、取离线消息 → 秒级恢复；
- 下行消息：owner 心跳缺失期间走回落（broadcast / 离线队列），最坏 30s 内不再投递死节点。
- **主动补一句**：恢复是「设备重连触发 + 心跳判定」驱动，不是主动接管——主动接管扫描器是我们阶段 3 的演进项。

### B5. 为什么不做主动接管扫描器？
**参考**：当前「重连触发」简单可靠，覆盖绝大多数场景（设备普遍会重连）；短板是僵尸连接（设备不回连）会一直占着 owner 记录。演进：周期扫描心跳超时 owner → 主动释放连接锁 + 迁移订阅/离线消息 + 通知 access 重路由，配合一致性哈希让重连落点可预测。

### B6. 连接锁在 Redis，Redis 单点/脑裂怎么办？⚠️
**参考**：当前 Redis 主从（或哨兵），脑裂可能双主——**已知风险，不回避**。答法：
- 业务容忍度分析：连接锁脑裂最坏结果是同一设备同时连两个节点，设备协议层通常只认一个 broker，靠心跳 + 重连收敛，容忍度较高；
- 若要求严格唯一：etcd/ZooKeeper lease（会话过期自动释放、强一致），或 Redlock（非绝对安全）。
- 结论：**按锁语义选存储**——允许极小概率双主用 Redis + 心跳兜底，严格唯一上 etcd。

### B7. 死节点 owner 期间，下行消息去哪了？会丢吗？
**参考**：`resolveOwnerNode` 解析目标节点时联合判定心跳；owner 已死 → 不投 `mqtt.down.{nodeId}`，改投 broadcast 回落或写离线队列，新节点接管后补发。**已知缺口**：owner 判定与心跳未完全联合时消息可能滞留（阶段 3 修复项，memory 已记录）。答完补演进方案，展示你清楚边界。

### B8. 发布限流怎么做？粒度？
**参考**：`PublishRateLimiter` 令牌桶，**按设备维度**限发布频率（桶容量/速率配置化，`rateLimitBucketCapacity` 默认 20 万）；超限直接拒绝并打 `mqtt.rate.limited` 指标。另有连接认证信号量 `authSlots`、会话恢复信号量 `sessionRestoreSlots`，防重连洪峰打挂节点。**强调**：限流要覆盖「连接数、认证速率、发布速率」三个维度，只限发布不够。

### B9. 共享订阅 $share 怎么实现？
**参考**：`$share/{group}/{filter}` 剥前缀后按真实 filter 匹配，同一原始 filter 的订阅者组成共享组（`LocalSubscriberIndex`），投递时组内轮询分发，实现消费者横向扩展。设备侧用共享组订阅自己的 down 通道，天然支持多 Broker 节点负载。

### B10. Netty 线程模型？EventLoop 上为什么不能阻塞？慢路径怎么处理？
**参考**：Netty 单线程串行处理一个 channel 的所有事件，EventLoop 阻塞会拖垮同线程上的所有连接（**一个慢操作 = 整批连接假死**）。我们铁律：**EventLoop 只做解析与快速路由，Redis/Kafka/DB/持久化全部 offload 到 brokerExecutor 线程池**；写数据走 Channel 写缓冲 + 水位背压，防 OOM。这是从 Netty 源码实践（channelRead 事件循环）总结的。

### B11. 百万级连接内存怎么估算？⚠️（可讲很深，是亮点题）
**参考**（五层纵深）：
- 内核：`fs.file-max` 约 400 万、`epoll max_user_watches`、`somaxconn`、conntrack、`tw_reuse`；
- JVM：ZGC + 直连内存，每连接堆内预算控制在 ~20KB；
- Netty：Epoll 模式（2×核数 EventLoop）、PooledAllocator、写缓冲背压；
- Broker：brokerExecutor offload、心跳统一时间轮扫描（避免每连接一个 timer）；
- 外部化：会话/订阅/离线消息全在 Redis/Kafka，不在堆内。
**结论**：100W 连接 ≈ 16-20GB 堆，64-128G 机器可支撑；**100W 连接 ≠ 100W 吞吐**，满吞吐场景单机建议 ≤20W 连接。压测注意：单台压测机受 `ip_local_port_range`（~3.2 万）限制，100W 需 4+ 台压测机或多源 IP。

### B12. Kafka 三通道怎么分工？QoS1 可靠性怎么保证？
**参考**：`mqtt.uplink`（设备→云，access 唯一消费组保序）、`mqtt.down.{nodeId}`（按连接锁 owner 定向）、`mqtt.broadcast`（KICK/回落/广播）。**QoS1 = 写 Kafka 成功才回 PUBACK**，从根上保证 at-least-once；消费端幂等去重。这一条是把「Broker 可靠」落到工程的关键证据。

## C. 储能 EMS 与领域（6 题）

### C1. EMS 充放电执行闭环讲讲？
**参考**：策略配置 → 计划生成（时段充放功率序列）→ **安全包络校验**（SOC 上下限/功率限值/温度边界，超限拒单）→ 时序落库 → 到点下发（command 经 down 通道）→ 设备 ACK 回写 → **状态机收敛**（下发中/已执行/超时补记/失败告警）。防悬挂：计划执行状态机带超时与补偿，错过窗口自动补记。

### C2. 峰谷电价怎么推导充放窗口？
**参考**：目标函数 = 最大化套利收益（放电收益 − 充电成本），约束 = 容量/SOC/功率/循环寿命；按电价时段分段扫描，输出最优充放功率曲线。进阶（加分）：结合需量电费削峰、电池衰减成本做多目标优化。

### C3. 需量管理 15 分钟滑窗怎么实现？
**参考**：需量 = 15 分钟平均功率最大值。按分钟粒度滚动累加窗口、滑动计算均值，检测最大需量逼近合同值 → 触发削峰策略（降充电功率/短时放电），多设备协同估算削峰节费。注意滑窗数据对齐与边界。

### C4. 指令下发失败 / ACK 超时怎么办？
**参考**：command 下发后进入 ACK 等待态，超时退避重试，重试上限后置失败并告警；设备状态机回退/补记；下行 QoS1 保证至少一次，业务侧幂等。**关键**：状态不能悬挂——所有等待态都要有超时路径。

### C5. VPP 你实际做过吗？⚠️（诚实 + 设计思路）
**参考**：没有直接上线过 VPP 聚合调度，但**策略引擎、需量管理、多设备协同削峰是 VPP 的底层能力**（聚合资源 + 统一调度）。设计思路：资源聚合层（集团→站→柜→簇分层建模已有）→ 调度编排层（现有策略引擎扩展为批量调度）→ 对接口（电力市场/聚合商 API）。**讲清已有资产如何复用**，比假装做过更打动人。

### C6. 你凭什么适配阳台储能？（JD 核心必问）
**参考**：储能本质是 **PCS + BMS + EMS 三件套**，工商业与阳台/户用只是功率等级（100kW 级 vs 3-10kW）、电压等级（三相 vs 单相）差异；充放电策略、安全包络校验、计划状态机、设备接入方法论完全可迁移，而且**阳台储能更简单**——无需需量管理、收益模式主要是峰谷套利 + 自发自用。我缺的是产品细节（C 端设备量大、协议多样 Modbus/MQTT/私有），这是增量不是存量差距。

## D. 高并发与通用架构（6 题）

### D1. 峰值 QPS 多少？扛住了什么场景？
**参考**：物联网中台日均百万级请求（网关层），单机 10w+ 长连接、5w+ 设备集中重连零故障。最难的场景是**断电恢复重连洪峰**——用连接/认证/发布三层限流 + 异步削峰 + 接入层水平扩展 + 优雅降级（拒新保旧）。

### D2. 限流算法对比？
**参考**：固定窗口（有突刺）/ 滑动窗口（精确但耗内存）/ 漏桶（恒定速率、平滑但突发响应差）/ **令牌桶**（允许突发，我们发布限流用的令牌桶）。分布式限流：Redis + Lua 原子操作，或网关层 Sentinel。

### D3. 缓存穿透 / 击穿 / 雪崩？
**参考**：穿透（查不存在）→ 布隆过滤器/空值缓存；击穿（热点 key 过期）→ 互斥锁/逻辑过期；雪崩（大量 key 同刻过期）→ 过期时间加随机 + 多级缓存 + 熔断降级。结合项目：Redis 缓存设备影子、凭据、配置等热点。

### D4. Redis 分布式锁的坑？
**参考**：`SETNX + EXPIRE` 非原子 → `SET NX EX` 原子；锁误删 → Lua 比较 value；锁过期业务未完成 → 看门狗续期；主从切换丢锁 → Redlock/etcd。**连接锁设计就是这套方法论的项目级应用**——能呼应上会非常加分。

### D5. TDengine 为什么选它？对比过什么？
**参考**：时序写入吞吐（百万点/秒级）、列式压缩（10 倍+）、超级表 + 自动建子表（按产品分库 `st_prop_*`）、连续查询降采样（原始→分钟/小时聚合）、保留策略滚动清理。对比：InfluxDB 单机写入瓶颈、MySQL 数据膨胀。注意主动提短板：TDengine 生态与周边工具不如 MySQL、3.x 集群运维成本。

### D6. Kafka 消费积压怎么办？
**参考**：监控 lag → 扩容消费者（受分区数上限约束，**分区数要按峰值容量提前规划**）→ 升级分区需重新哈希、代价大 → 兜底：热点场景旁路 Redis/本地队列。生产者侧：批大小、acks、限流参数调优。

## E. 诚实性雷区（5 题）⚠️ 全组高风险

### E1. JD 要 5 年储能架构经验，你实际多久？
**参考**（组合叙事，不虚标）：坦诚储能平台 1 年，但 **IoT 平台架构 5 年**——百万级设备接入、高并发、MQTT/Netty、时序库、多租户 SaaS 是同一套技术栈；储能领域 90% 的复杂度在平台（接入/可靠性/调度引擎），领域知识（PCS/BMS 通信、电力市场）是增量，正在快速补齐。**讲「架构复用」不讲「年限换算」**。

### E2. K8s 有生产经验吗？⚠️（JD 硬要求，最危险）
**参考**：**没有就直说**，然后给方案——
- Docker 容器化已落地；
- K8s 演进路径我清晰：Deployment/StatefulSet（有状态服务如 TDengine）、HPA（按连接数/CPU）、探针与优雅停机（配合 Broker 心跳）、Ingress 网关；
- 我了解核心原理（Pod 调度、etcd 一致性、CNI 网络）。
**面试官更怕不懂装懂，怕的是没方案。** 主动说"这块是我入职后要快速补的实操短板，但架构认知已就位"。

### E3. 49ms 是生产数据吗？
**参考**：见 B1。主动拆分「联调基准 vs 生产统计」口径。

### E4. 「百万级设备」实际接入了吗？
**参考**：见 A5。设计容量与当前规模分开说，绝不混淆——一旦被追问"那你们实际多少台"，前后矛盾就是诚信问题。

### E5. 简历写「30s 恢复」，设备 5 分钟不重连怎么办？
**参考**：两个时间维度分开讲——**恢复窗口**（心跳 TTL 30s，重连即接管）和**离线保留**（会话/离线消息在 Redis 按 TTL 保留，超期才重建）。设备回来即恢复；不回来时下行走离线队列，不丢。这题答好 = 展示你理解「恢复」和「离线」是两个概念。

## F. 反问面试官（4 个高质量问题）

1. **业务阶段**：阳台储能目前出货规模/接入设备量？平台处在 0→1 还是规模化阶段？（判断是去建设还是去救火）
2. **云边协同形态**：你们说的云边协同具体是边缘网关形态还是设备直连？团队怎么分工？（体现你懂行且关注协作面）
3. **VPP 规划**：VPP 是已有客户还是规划？对接的是现货还是辅助服务市场？（体现对增值场景的理解）
4. **K8s 主导权**：云原生落地是你们团队主导推进还是已有平台？我进来主要接哪块？（反向确认职责边界与 JD 一致性）

## 附：答题总原则

1. **先结论后细节**：一句话结论 → 机制/数据 → 边界与演进，控制在 1-2 分钟内。
2. **所有数字要能对口径**：49ms（联调基准）、30s（心跳 TTL）、百万级（设计容量）——被追问时主动拆口径。
3. **雷区题先认缺口再给方案**：K8s、储能年限、主动接管——面试官要的是「知道边界 + 有演进路径」，不是完美履历。
4. **把已知缺口变成展示点**：连接锁单点、下行滞留这些"缺口"恰恰证明你在真实生产里思考过，比背八股文有价值。
